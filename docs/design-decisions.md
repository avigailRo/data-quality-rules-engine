# החלטות תכנון (Design Decisions)

המסמך מרכז את ההחלטות ההנדסיות המרכזיות: מה נבחר, אילו חלופות נשקלו ולמה, איך מרחיבים את המערכת ומה המצב המדויק של כל רכיב.

## ההחלטות הארכיטקטוניות המרכזיות

| # | החלטה | למה | חלופות שנשקלו |
| --- | --- | --- | --- |
| 1 | **בקרה = Typed Rule AST ב־JSON**, ולא SQL ולא שפה חופשית | מאפשר ולידציה מלאה, אבטחה (אין טקסט שהופך ל־SQL), UI גנרי, הסברים, ושימוש באותו פורמט גם להצעות AI | SQL שמור לכל בקרה (לא בטוח ולא גנרי); Dynamic LINQ ב־EF (קשה לשלוט ב־SQL וב־NULL); DSL טקסטואלי (דורש Parser, ומשתמש עסקי לא יכתוב אותו) |
| 2 | **Business Metadata Catalog** עם Key לוגי נפרד משם פיזי | המשתמש רואה מונחים עסקיים בלבד; הקטלוג הוא גם ה־Allowlist של המזהים; ישות חדשה = שורות Metadata בלבד | קריאת `INFORMATION_SCHEMA` ישירות (חושפת שמות טכניים, אין שמות עסקיים) |
| 3 | **סמנטיקה דו־ערכית מפורשת + EXISTS ל־One-to-Many** | NULL לא "מעלים" רשומות תחת NOT, ‏none או all; אין כפילויות JOIN ואין צורך ב־DISTINCT | להשאיר את ה־3VL של SQL (באגים שקטים); JOIN + DISTINCT (איטי ומסתיר באגים) |
| 4 | **הרשאות במסד עצמו**: הבקרות רצות כ־`dc_rule_reader` עם SELECT על `biz` בלבד | גם באג עתידי בקומפיילר לא יכול לשנות נתונים או לקרוא הגדרות. Defense in Depth | לסמוך רק על ולידציה בקוד; Regex או Blacklist של מילים (לא אמין) |
| 5 | **הפרדה בין הגדרה להרצה**: RuleVersion בלתי משתנה, תור הרצות, ושמירת חריגות לכל הרצה | היסטוריה אמינה (איזו גרסה רצה), דפדוף עקבי, ואין Timeout של HTTP על שאילתה ארוכה | הרצה חיה בכל דפדוף (לא עקבי ויקר) |

## איך מוסיפים בקרה חדשה (ללא קוד)

במסך "בקרה חדשה": בוחרים נושא, בונים תנאים, צופים בתצוגה מקדימה, שומרים ומריצים. ה־JSON נשמר ב־`dq.Rule`, ובכל שמירה נוצר Snapshot ב־`dq.RuleVersion`.

## איך מוסיפים ישות חדשה (ללא שינוי במנוע)

1. יוצרים טבלה בסכמה `biz`. הרשאת הקריאה מתקבלת אוטומטית מה־GRANT על הסכמה.
2. מוסיפים שורות ל־`dq.Entity`, ‏`dq.Field` ו־`dq.Relationship` (ראו `db/06_seed_metadata.sql`).
3. מנהל מערכת מריץ "אימות הקטלוג", שבודק מול `sys.columns` ש־Key ויחס "אחד" ייחודיים, ונטען מחדש.
4. הישות זמינה מיד בבונה הבקרות ובמנוע ההמלצות.

## איך מאובטח מנוע ה־SQL

1. ‏JSON מטופס, ושדות לא מוכרים נדחים (למשל `"sql": ...`).
2. ‏Bind מול הקטלוג: כל מזהה חייב להיות Key רשום. השם הפיזי נלקח מהקטלוג, לא מהבקשה.
3. האופרטורים הם enum סגור ונכתבים מ־switch קבוע. מזהי הצמתים לא נכנסים ל־SQL; ה־Aliases (`t0`, ‏`f0`) מיוצרים על ידי המנוע.
4. מזהים בסוגריים מרובעים עם הכפלת `]`; כל ערך הוא `SqlParameter` מוקלד. ב־LIKE, התווים `%`, `_` ו־`[` מוסקפים.
5. ‏`EXECUTE AS USER = 'dc_rule_reader'`: ‏SELECT על `biz` בלבד ו־DENY על `dq`, ללא Pooling.
6. מגבלות: עומק 6, ‏60 צמתים, ‏200 ערכים, Timeout של 30 שניות, ותקרה של 10,000 חריגות שמורות.
7. ‏Authorization Policies בשרת: ‏Viewer, ‏RuleAuthor, ‏RuleRunner ו־CatalogAdmin.

**ראיות:** בדיקות היחידה (`RuleEngineTests`), וסקריפט ה־QA שמריץ 7 תרחישי תקיפה מול ה־API ובודק שטבלת העובדים נשארה שלמה, ושמשתמש ההרצה נדחה ב־UPDATE, ב־CREATE ובקריאה מ־`dq`.

## איך עובד מנגנון ה־AI

```text
.NET (קטלוג) ─► Python: Profiler ─► Provider ─► ולידציה ב־Pydantic (+ סבב תיקון אחד) ─► Fallback מקומי
                (dc_profiler, אגרגציות)                                                    │
.NET: RuleBinder (אותו Validator כמו לבקרה ידנית) ─► dq.AiSuggestion (Proposed) ─► אישור אנושי ─► Rule בסטטוס Draft
```

- **Providers** (נבחרים ב־Configuration בלבד):
  - `heuristic` (ברירת מחדל): ניתוח מקומי דטרמיניסטי.
  - `openai`: כל API תואם OpenAI, כולל Gemini (ה־Endpoint התואם של Google) ו־Ollama מקומי ב־`.../v1`.
  - `vertex`: ‏Gemini ב־GCP.
- **Structured Output:** ‏JSON Schema ב־`response_format` (וב־`response_schema` ב־Vertex). אחר כך ולידציה מחמירה ב־Python, ושוב ב־.NET.
- **ה־LLM לא כותב SQL:** אין שדה SQL בסכמה, הוא לא מכיר שמות פיזיים, וכל מחרוזת שהוא מחזיר היא Key (שעובר Bind) או ערך (שעובר כפרמטר).
- **פרטיות:** ה־LLM מקבל רק שמות עסקיים, טיפוסים, קשרים וסטטיסטיקה מצטברת, ללא רשומות. כשה־Endpoint חיצוני, נתונים סטטיסטיים של שדות רגישים לא נשלחים בכלל.
- **שקיפות:** כל הצעה מסומנת "מודל שפה" או "ניתוח מקומי". הניתוח המקומי לא מוצג כ־LLM.
- **עמידות:** ‏Timeout, ‏Fallback מקומי כש־LLM נכשל, ותשובת 503 מסודרת כשהשירות כבוי, בזמן ששאר המערכת עובדת.

## מצב אינטגרציית ה־LLM

- **מה פעיל ומאומת:** הניתוח המקומי. צינור הוולידציה, ה־Fallback וסבב התיקון נבדקו ב־pytest מול LLM מדומה (Fake).
- **הדרישה:** שימוש ב־AI כדי להציע בקרות על בסיס ה־Metadata והנתונים.
- **בדיקה חיה:** ‏Gemini דרך ה־Endpoint התואם OpenAI, עם אותו Adapter בלי קוד ייעודי. הסקריפט `qa/run-llm-e2e.ps1` בודק את כל השרשרת: Metadata ← LLM ← ולידציה ← אישור ← בקרה שמורה ← הרצה, ובנוסף Fallback עם מפתח שגוי.
- **מה הוכח בפועל:** המפתח מאומת. ‏TLS עובד גם ברשת עם TLS Inspection. מפתח שגוי מקבל HTTP 400 אמיתי מ־Gemini, והמערכת עוברת לניתוח המקומי ומסמנת זאת נכון. שום בקרה לא נשמרת בלי אישור.
- **מה לא הוכח:** המלצה שנוצרה בפועל על ידי Gemini. עם מפתח תקין התקבלו 503 (המודל עמוס) ו־Timeout, גם לבקשה זעירה. לא אומת אם הסיבה בצד של Google או ברשת המקומית.
- **ממצאי הבדיקה החיה ותיקונים:** ניסיון חוזר על 429/5xx, מודל חלופי, ובעיקר תקציב זמן כולל. בבדיקה הראשונה ה־Fallback לא הספיק לענות לפני ה־Timeout של ה־API, וזה היה באג אמיתי שהבדיקה החיה חשפה.
- **לא נבדק מול השירות:** ה־Adapter ל־Vertex AI. בייצור על GCP זה המסלול הטבעי (Service Account במקום מפתח).
- **איך מפעילים:**
  - Ollama מקומי (הנתונים לא יוצאים מהמחשב):
    ```
    set DQ_LLM_PROVIDER=openai
    set DQ_LLM_BASE_URL=http://localhost:11434/v1
    set DQ_LLM_MODEL=qwen2.5:7b
    ```
  - OpenAI: גם `DQ_LLM_API_KEY`, ממשתנה סביבה או מ־Secret Manager, ולעולם לא בקוד.

## שיפורים לייצור (Roadmap)

- ‏OIDC אמיתי (Identity Platform או Entra) במקום משתמשי דמו, ו־Logins נפרדים או Managed Identity במקום EXECUTE AS.
- תור מתמיד (Pub/Sub או Cloud Tasks) ותזמון הרצות (Cloud Scheduler), עם התראות על עלייה בחריגות.
- בדיקות אינטגרציה עם Testcontainers ב־CI, ובדיקות E2E עם Playwright.
- ‏Masking לשדות רגישים בתוצאות, והרשאות לפי ישות.
- אגרגציות ותנאי ספירה על רשומות קשורות.
- ‏Full-Text Search בתוצאות.
- ‏OpenTelemetry ו־Dashboards.
- הערכת איכות של הצעות ה־LLM (שיעור קבלה ודחייה) לשיפור ה־Prompt.
