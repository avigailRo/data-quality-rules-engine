# ארכיטקטורה ומנגנון הבקרות

## עקרונות

1. **בקרה היא נתון, לא קוד.** בקרה נשמרת כעץ JSON מטופס (Rule AST). בקרה חדשה היא שורה ב־`dq.Rule`, וישות עסקית חדשה היא שורות ב־Metadata.
2. **אף מחרוזת מהמשתמש או מה־LLM לא הופכת ל־SQL.** מזהים מגיעים רק מה־Catalog, וערכים מגיעים רק כפרמטרים מוקלדים.
3. **מסלול ולידציה אחד לכולם.** בקרה של משתמש והצעה של AI עוברות דרך אותו `RuleBinder` ואותו Compiler.

## רכיבים

```text
Angular SPA ──REST /api/v1──► ASP.NET Core API ──HTTP פנימי──► dq-advisor (Python/FastAPI) ──► LLM Provider
                                   │                                  │
                                   ▼                                  ▼
                       SQL Server: dq (מערכת)  ·  biz (נתונים עסקיים)  ◄── קריאה בלבד
```

| שכבה | אחריות |
| --- | --- |
| Domain | מודל ה־Catalog, ה־Rule AST, ה־Binder וה־Validator, קטלוג אופרטורים ופונקציות, מנוע ההסברים בעברית. ללא תלויות חיצוניות. |
| Application | Use cases לפי פיצ'ר (Rules, Runs, Suggestions) וממשקים (Ports). אין כאן SQL. |
| Infrastructure | `SqlServerRuleCompiler`, ‏`SqlServerRuleQueryExecutor`, Repositories (Dapper), Catalog Loader ו־Verifier, תור הרצות ו־Worker, Client לשירות ה־AI. |
| Api | Minimal APIs, מדיניות הרשאות (Policies), ProblemDetails, Health checks. |

## מחזור החיים של בקרה

1. **הגדרה.** המשתמש בוחר נושא ובונה תנאים במונחים עסקיים. כל שינוי נשלח ל־`/rules/validate`, שמחזיר משפט תקציר בעברית ושגיאות לפי מזהה תנאי.
2. **שמירה.** הבקרה נשמרת ב־`dq.Rule`, וכל שמירה יוצרת Snapshot בלתי משתנה ב־`dq.RuleVersion`. עדכון דורש `If-Match` (מניעת דריסה מקבילית, 412).
3. **הרצה.** ‏`POST /rules/{id}/runs` מחזיר 202. ‏Worker ברקע מריץ את **הגרסה המדויקת** של הבקרה, ושומר ספירה מלאה ועד 10,000 חריגות עם הסבר לכל אחת.
4. **תוצאות.** דפדוף, חיפוש וסינון לפי סיבת החריגה, על הנתונים השמורים של אותה הרצה.

## צינור המנוע

`Parse → Bind → Validate → Compile → Execute → Explain`

- **Parse:** ‏`System.Text.Json` פולימורפי. שדות לא מוכרים נדחים (`UnmappedMemberHandling.Disallow`).
- **Bind ו־Validate:** כל Key מוצמד לאובייקט Catalog. נבדקים אופרטור מול טיפוס, תאימות טיפוסים בהשוואת שדה לשדה, ערכי Enum, נתיבים (מותר לעבור רק בקשרי Many-to-One) ומגבלות (עומק 6, עד 60 צמתים, עד 200 ערכים ברשימה). השגיאות נאספות כולן ולא רק הראשונה.
- **Compile:** ‏SQL נבנה רק ממילות מפתח קבועות, ממזהים מהקטלוג בסוגריים מרובעים, מ־Aliases שהמנוע מייצר (`t0`, ‏`f0`, ‏`v0`) ומפרמטרים. מזהי הצמתים מהבקשה לעולם לא נכנסים ל־SQL.
- **Execute:** ‏`EXECUTE AS USER = 'dc_rule_reader'`, משתמש עם `SELECT` על הסכמה `biz` בלבד. החיבור הוא ללא Pooling, עם `CommandTimeout`, ועם שתי שאילתות: `COUNT_BIG` מלא, ו־`TOP (@cap)` עם עמודות הסבר.
- **Explain:** לכל עלה בהיקף הראשי מחושב דגל `CASE WHEN … THEN 1 ELSE 0 END`. העץ מוערך בזיכרון, ומוחזר תת־העץ המינימלי שגרם לחריגה (בקבוצת OR, רק הענפים שהתקיימו), יחד עם הערכים בפועל.

## החלטות סמנטיות

| נושא | פתרון |
| --- | --- |
| NULL ולוגיקה תלת־ערכית | כל עלה מקומפל לפרדיקט דו־ערכי: על כל אופרנד nullable מתווסף `IS NOT NULL`. לכן `NOT`, ‏`none` ו־`all` לא מפסידים רשומות בשקט. הכלל העסקי: "שדה ריק לא מקיים אף השוואה; לבדיקת ריקות משתמשים ב'ריק'". |
| שדה דרך LEFT JOIN | נחשב nullable גם אם העמודה עצמה NOT NULL. |
| One-to-Many | ‏`EXISTS` / `NOT EXISTS` מתואם, ואף פעם לא JOIN. כך אין כפילויות ואין צורך ב־DISTINCT. ‏`all` = ‏`NOT EXISTS (… AND NOT cond)`. |
| Many-to-One | ‏LEFT JOIN, עם Alias אחד לכל נתיב (שימוש חוזר). ה־Verifier בודק שצד ה"אחד" ייחודי. |
| ריק במחרוזת | `IS NULL OR LTRIM(RTRIM(x)) = N''`. |
| LIKE | התווים `%`, `_` ו־`[` מוסקפים בעזרת `ESCAPE`. |
| גיל | שדה מחושב מקטלוג פונקציות סגור (`ageYears`), לפי פרמטר `@__today` (דטרמיניסטי וניתן לבדיקה). |
| טיפוסי פרמטרים | נקבעים לפי ה־Metadata של העמודה, כדי למנוע המרות מרומזות. |

## אבטחה (Defense in Depth)

1. AST מטופס, דחיית שדות לא מוכרים ומגבלות גודל.
2. ‏Bind מול הקטלוג: אין מזהה שאינו Key רשום.
3. ‏Verify של הקטלוג מול `sys.columns`, ורק הסכמה `biz` מותרת.
4. ‏Quoting של מזהים ב־Renderer.
5. פרמטרים מוקלדים לכל ערך.
6. הרשאות במסד עצמו: `dc_rule_reader` עם `SELECT` על `biz` בלבד ו־`DENY` על `dq`.
7. ‏Timeout ותקרת תוצאות.
8. ‏Authorization Policies: ‏Viewer, ‏RuleAuthor, ‏RuleRunner, ‏CatalogAdmin.

האבטחה לא נשענת על Regex או על חסימת מילים.

## הוספת ישות עסקית חדשה (ללא שינוי קוד)

1. יוצרים את הטבלה בסכמה `biz`. הרשאת הקריאה מתקבלת אוטומטית מה־GRANT על הסכמה.
2. מוסיפים שורות ל־`dq.Entity`, ‏`dq.Field` ו־`dq.Relationship` (ראו `db/06_seed_metadata.sql`).
3. מנהל מערכת לוחץ על "אימות הקטלוג". הקטלוג נטען מחדש ונבדק מול מבנה המסד.
4. הישות זמינה מיד בבונה הבקרות ובמנוע ההמלצות.

## ביצועים ועמידות

**מה ממומש:**
- **שאילתה אחת לכל בקרה, בצד השרת:** המנוע מתרגם את כל הבקרה ל־SQL אחד. אין שליפה של רשומות לזיכרון ואין N+1.
- **קשרים בלי שכפול שורות:** קשר Many-to-One מתורגם ל־`LEFT JOIN` אחד לכל נתיב, גם אם כמה תנאים משתמשים בו. קשר One-to-Many מתורגם ל־`EXISTS` או `NOT EXISTS` מתואם, ולכן אין שכפול שורות ואין צורך ב־`DISTINCT`.
- **אינדקסים:** על כל מפתחות הזרים ועל עמודות הסינון הנפוצות בנתוני הדוגמה (`db/02_biz_schema.sql`). ה־`EXISTS` נשען עליהם.
- **מגבלות משאבים:**
  - ‏`CommandTimeout` של 30 שניות.
  - ‏`COUNT_BIG` לספירה המלאה, ו־`TOP(@__cap)` שמגביל את מספר החריגות שנשמרות (10,000).
  - מגבלות על מבנה הבקרה: עומק 6, עד 60 צמתים, עד 200 ערכים ברשימה.
  - הצפייה בחריגות מחולקת לדפים, עד 100 רשומות בדף.
- **הרצה אסינכרונית:** בקשת הרצה מחזירה 202 מיד. ההרצה נכנסת לתור חסום (Channel) ש־BackgroundService מעבד, וה־API לא ממתין לבסיס הנתונים. החריגות נשמרות ב־`SqlBulkCopy` ולא שורה אחר שורה.
- **מטמון:** הקטלוג נטען לזיכרון פעם אחת, וב־Compiler פרדיקט שחוזר בבקרה מחושב פעם אחת.
- **שירות ה־AI לא מעכב שום דבר:** יש מגבלת זמן כוללת, Fallback מקומי, ו־503 מסודר כשהשירות כבוי. הבקרות ממשיכות לרוץ.

**מגבלות ידועות, ומה הייתי עושה בייצור:**
- **שדות מחושבים** (למשל גיל מתוך תאריך לידה) ו־`contains` עם תו כללי בתחילת המחרוזת לא יכולים להשתמש באינדקס. בייצור: עמודה מחושבת עם אינדקס, או Full-Text Search.
- **שני מעברים על הנתונים:** ספירה ושליפת החריגות מתבצעות בשני מעברים, וזה פשוט ובטוח. בטבלאות גדולות מאוד אפשר לשמור קודם את המפתחות בטבלה זמנית.
- **תפוקה:** ‏Worker יחיד מריץ בקרה אחת בכל פעם, וזה מגן על בסיס הנתונים התפעולי. בייצור: כמה Workers עם מגבלת מקביליות, הרצה על Read Replica, ותזמון בשעות שפל.
- **אינדקסים לבקרות חדשות** לא נוצרים אוטומטית. בייצור: מעקב אחרי `SqlHash` ומשך הריצה (שכבר נשמרים לכל הרצה), כדי לזהות בקרות יקרות ולהוסיף להן אינדקסים.

## הוספת סוג בקרה חדש (אופרטור)

אופרטור הוא "סוג בקרה" במנוע. נניח שמוסיפים `notContains`. השינויים מרוכזים במקומות קבועים, וכל אחד מהם נבדק בבדיקות יחידה:

1. **`Domain/Rules/Ast/RuleAst.cs`:** ערך חדש ב־enum `Operator`. ה־enum סגור, ולכן JSON עם אופרטור לא מוכר נדחה כבר בשלב ה־Parse.
2. **`Domain/Rules/OperatorCatalog.cs`:** לאילו טיפוסים האופרטור מותר, ואיזה ערך בצד ימין הוא מצפה. מכאן ה־Binder בונה את מטריצת אופרטור × טיפוס, ומכאן ה־API מחזיר את רשימת האופרטורים לממשק (`/api/v1/catalog/operators`).
3. **`Infrastructure/SqlServer/SqlServerRuleCompiler.cs`:** ענף חדש ב־switch שמייצר SQL מפורמט עם פרמטרים בלבד, כולל טיפול ב־NULL לפי הסמנטיקה הדו־ערכית.
4. **`Domain/Rules/Explain/RuleDescriber.cs`:** הנוסח העברי שמופיע בסיכום הבקרה ובהסבר של כל חריגה.
5. **Python** (רק אם רוצים שה־AI יוכל להציע אותו): `models.py` (‏`OperatorName`), `validation.py` (טיפוסים מותרים) והמדריך בפרומפט ב־`providers.py`.

**הממשק לא משתנה:** בונה הבקרות טוען את רשימת האופרטורים מה־API, ולכן האופרטור החדש מופיע בו אוטומטית לטיפוסים המתאימים.

## המלצות AI

- **Python** מקבל מה־API את הקטלוג, מריץ פרופילינג בטוח (אגרגציות ודגימה מוגבלת) כ־`dc_profiler`, ומפיק המלצות **בפורמט ה־AST בלבד**.
- **Providers:** מנוע כללים סטטיסטי (ברירת מחדל, ללא מפתח), Ollama (LLM מקומי) ו־Vertex AI Gemini (GCP). אם LLM נכשל, השירות נופל חזרה למנוע הכללים.
- **ה־LLM לא רואה** שמות טבלאות או עמודות ולא רואה רשומות. הוא רואה Keys, שמות עבריים, טיפוסים וסטטיסטיקה מצטברת. בשדות רגישים הוא רואה רק את אחוז הערכים החסרים.
- **ולידציה כפולה:** ‏Pydantic מחמיר בצד Python (שדה `sql` נוסף נדחה), ואחריו ה־`RuleBinder` הסמכותי ב־‎.NET. הצעה לא תקינה נשמרת כ־`Invalid` עם הסיבה, כדי שיהיה שקוף מה נפסל.
- **אישור אנושי:** הצעה מאושרת הופכת לבקרה בסטטוס **טיוטה** בלבד. הרצתה היא פעולה נפרדת של המשתמש.
